# 스터디룸 통합 운영·검증

2026-11-09 운영 전환. 기존 좌석 QR의 Apps Script 배포를 버전 12로 갱신했다. 학생은 QR에서 **출석 화면 열기**를 선택하고, 교사와 관리자는 통합시간표의 **스터디룸** 메뉴를 사용한다. 원본 시트와 배포 버전 11은 전환 전 기록을 확인할 때 사용한다.

## 운영 시정

모든 시간은 한국 시간이다. 회차 종료 시 접수를 닫고 현재 좌석 표시는 다음 회차를 기준으로 바뀐다. Cloudflare Cron이 1분마다 마감할 회차를 확인해 출석 기록을 보관한다.

| 운영일 | 오전 | 오후 | 야간 |
| --- | --- | --- | --- |
| 월·화·목·금 | 07:00–08:30 | 16:30–18:30 | 18:30–21:30 |
| 수 | 07:00–08:30 | 15:30–18:30 | — |
| 토 | 08:30–12:30 | 12:30–17:30 | — |

## 구성과 사용

- 시간표 교사·관리자 화면에 `스터디룸` 메뉴를 추가했다. 같은 Worker의 `/api/studyroom`, 같은 `env.DB`를 사용한다. 별도의 학생 명부를 수정·동기화하지 않고 시간표 `students`에서 직접 조회한다.
- 학생 화면은 `studyroom-student.html?seat=01`부터 `99`까지다. 이름 조회 → 확인 → 제출, 요청 ID를 유지한 통신 실패 재시도, 좌석 충돌 거절과 좌석 이동을 지원한다.
- 현재 출석은 원본 시트의 99석 배치와 목록을 제공한다. 수동 등록·이동·취소·복원·변경 이력은 현재 출석에서 처리한다. 출석 조회에서는 월 달력의 날짜와 회차를 눌러 해당 출석 표를 열고, 기존 비고는 읽기에서 수정하거나 삭제한다. 기록 없는 날을 결석으로 판정하지 않는다.
- 기존 교사 또는 관리자 로그인으로 비고를 저장하고 출석을 정정한다. 변경 이력에는 사용 권한(교사 또는 관리자)을 남긴다. 이전 확인 기록은 데이터에 보존한다.
- 관리자에서 이용 허용, 이전 학생 이력 연결, 적용일·요일·접수 시작·저장/초기화 시정, 개별 계정, 출석 자료 내보내기를 관리한다. 접수를 중지해도 진행 중 회차의 교사 좌석 표시와 이력을 보존한다.
- 미니멀한 모노톤과 기존 화면 틀을 유지하고 같은 자체 호스팅 Pretendard를 사용한다. 자동 갱신은 표시 중인 현재 출석 화면에서 30초 간격이며, 탭 숨김·요청 진행·정정 창 표시 중에는 중단한다.

## 데이터 보존과 동시성

`0004_studyroom.sql`은 추가 테이블과 제약을 만들고, `0005_studyroom_record_guard.sql`은 기록별 동시 수정·마감 경계를 보호한다. `0006_studyroom_notes.sql`은 출석 비고를 추가하며 기존 기록은 빈 비고로 유지한다. 배포 시 이 마이그레이션을 Worker보다 먼저 적용한다.

- `student_people`, `student_person_links`는 공통 불변 식별자다. 학생 행을 삭제·재삽입하는 기존 명부 가져오기/복원에서도 연결과 출석을 지우지 않는다. 출석은 당시 학번·이름·학기·회차를 보존한다.
- 새 학기/학년도에 새 UUID가 생기면 첫 출석 전 관리자가 이전 이력을 확인해 연결한다. 이미 출석이 있는 두 식별자의 병합은 차단한다. 2026년 운영 전환 당시에는 과거 출석의 학번과 이름을 같은 학기 명부에 대조했다.
- 회차 ID는 기준 학기·서울 날짜·시정 버전·회차를 포함한다. 과거 조회는 현재 활성 학기에 갇히지 않는다. **현재 학생 조회 기준은 시간표의 활성 학기**이므로 운영 중 과거 자료를 볼 때는 출석 조회를 사용한다.
- `sr_attendance`는 학생·회차당 하나이며 활성 좌석에 고유 제약을 둔다. `sr_events`에 요청 ID·원장 스냅샷·주체·사유를 남긴다. 같은 UUID를 다른 내용에 재사용하면 거절한다.
- D1 batch 트랜잭션과 DB 검사로 원장·현재 상태·권한·버전을 함께 확인한다. 다른 학생의 입실은 전역 출석 버전에 잠그지 않고, 정책 버전·동일 학생 기록 버전·고유 제약으로 보호한다. 입실이 시간표 전체 수정 버전을 올리지는 않는다.
- 비고·정정은 출석 버전과 현재 세션을 트랜잭션 안에서도 확인한다. 다른 학생의 입실은 해당 출석의 비고 저장을 막지 않는다. 마감이 먼저 완료되면 늦은 제출은 거절된다. 전체 명부와 정정 기능은 교사 또는 관리자 인증을 요구한다.

## QR 유지

호환 진입 코드의 템플릿은 `apps-script-bridge/Code.gs`에 있다. 기존 `/exec?seat=NN`을 받고 Cloudflare 학생 화면에 좌석을 전달한다. 운영 배포는 대상 Worker 주소를 코드에 고정한다.

Google HtmlService의 이동 제한 때문에 **출석 화면 열기** 버튼으로 새 화면을 연다. 조회·제출·교사 화면·자동 마감은 Cloudflare가 처리하고 Apps Script에서 매번 중계하지 않는다. 첫 QR 접속의 Google 의존성은 남는다.

별도 Google 프로젝트를 소유자 전용 웹앱으로 배포해 99번 QR의 Google 진입 화면 → 버튼 → 실제 Cloudflare 99번 화면 이동과 접수 종료 거절을 확인했다. 테스트의 연결 대상은 고정한 가상 Worker다. 프로젝트·배포 식별자는 인계 폴더의 `local-private/cloudflare-qr-test-deployment.json`에 보관한다. 현장 인쇄 QR·실제 학생 휴대전화 검증은 아직 하지 않았다.

기존 Apps Script 초기화 예약이 호출하는 함수는 데이터 변경 없이 끝난다. 전환 뒤 출석부와 좌석 현황은 통합시간표에서 확인한다. 전환 전 원본 시트와 복구용 Apps Script 소스는 별도로 보관한다.

## 자동 마감

학생 접수와 회차는 요청 때마다 서버 시각으로 판정한다. Cron 실행이 늦어도 마감 시각 이후 제출을 지난 회차에 받지 않는다. 교사 표시는 다음 갱신에 현재 회차를 따른다.

Worker의 `scheduled`가 기한이 지난 열린 회차를 원장과 함께 보존하고, 건수·JSON·SHA-256을 남겨 마감한다. 기록을 삭제해 초기화하지 않는다. 중복 실행은 같은 회차를 다시 마감하지 않으며, 실패하면 트랜잭션을 되돌리고 재시도한다. 한 실행에 회차 1개로 제한하고 미처리 회차는 다음 실행에서 처리한다. Cron은 UTC, 업무 날짜는 서울 기준이다. 초 단위 정각 실행을 보장하지 않는다.

마감 뒤의 교사 확인·정정은 별도 사건으로 추가하고 조회에 반영한다. 마감 시점의 아카이브 원본은 바꾸지 않는다.

운영 설정 `wrangler.jsonc`에 `STUDYROOM_ENABLED=true`, `STUDYROOM_CRON_ENABLED=true`, 1분 간격 Cron을 설정했다. 관리자에서 회차별 시정과 학생 접수 여부를 변경할 수 있다.

## 실행·복구

```sh
pnpm test
pnpm test:studyroom-browser
pnpm dev:studyroom
```

미리보기는 loopback 전용 가상 저장소다. 공통 교사/관리자 `1234`, 가상 학번 `30101`, `30102`를 사용하며 종료하면 초기화된다. 원격 테스트의 강한 임의 비밀번호는 `private/studyroom-test-credentials.local.json`에 별도로 보관하며 로컬 예시 비밀번호와 다르다.

원격 테스트 명령은 `scripts/studyroom-staging.mjs`가 이름·계정·단일 DB·운영 DB와 다른 ID를 검사한 후 실행한다. 현재 테스트 설정은 `.cache/studyroom-test.wrangler.json`이다. `deploy`, `secrets`, `migrate`, `cron-on`, `cron-off`, `export`는 이 격리된 대상에만 적용된다. 실제 운영 배포용 우회 명령으로 사용하지 않는다.

기존 시간표 JSON 백업/복원은 시간표 범위다. **스터디룸까지 전체 복구하려면 D1 전체 SQL export와 Worker의 기존 서버 비밀값을 함께 보존**해야 한다. 출석 자료 내보내기는 개인정보가 포함된 조회용 자료다. 전환 후 출석이 발생했다면 공유 D1 전체를 과거 시점으로 돌리기 전에 새 출석과 시간표 변경의 복구 범위를 확인한다.

예약 검증은 [Cloudflare 공식 Miniflare scheduled API](https://developers.cloudflare.com/workers/testing/miniflare/core/scheduled/), 운영 Cron은 [공식 Cron 문서](https://developers.cloudflare.com/workers/configuration/cron-triggers/)를 기준으로 했다.
